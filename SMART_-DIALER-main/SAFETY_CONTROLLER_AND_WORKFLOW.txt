1.1. WHY THE PREVIOUS TERMINAL OUTPUT SHOWED 0 ANSWERED CALLS (AND THE FIX)
--------------------------------------------------------------------------------
In the initial unscaled run:
• The assignment specifies real-world average talk times:
  - Scenario A: 120 seconds (2.0 minutes)
  - Scenario B: 90 seconds (1.5 minutes)
  - Scenario C: 180 seconds (3.0 minutes)
• The CLI simulation was set to run for 60 seconds (1.0 minute).
• Because 120s / 180s talk times were longer than the 60s test window, calls that
  were answered remained actively CONNECTED on the line and had not reached
  terminal COMPLETED status before the test ended.
• Additionally, the counter was reading completed dispositions rather than active
  answered calls.

THE FIX:
1. Updated `CallStateMachine.getStats()` to immediately count all calls that transition
   to `ANSWERED` and `CONNECTED` states in real time.
2. Introduced 20x time compression into `dialer-simulator.ts`:
   - 120s real talk time is simulated in 6.0s
   - 6s real ring time is simulated in 300ms
   This allows hundreds of realistic call lifecycles (Initiate -> Ring -> Answer ->
   Talk -> Wrap-up -> Free agent) to fully execute in a 12-second test.
3. Updated `CallAllocator` so that in Predictive Mode, calls are initiated speculatively
   and connected to available agents immediately upon answer, with zero idle hold.

3. SAFETY CONTROLLER IMPLEMENTATION & ALGORITHMS
================================================================================

--------------------------------------------------------------------------------
3.1. ROLE OF THE SAFETY CONTROLLER AS AN UNBREAKABLE FIREWALL
--------------------------------------------------------------------------------
The Safety Controller is positioned strictly between the Pacing Engine and the
Telecom Provider / Call Allocator:

  Campaign
     │
     ▼
  Pacing Engine (Progressive / Predictive)  ---> Proposes: "Dial N calls"
     │
     ▼
  [★ SAFETY CONTROLLER (Firewall) ★]       ---> Decides: APPROVE | REDUCE | REJECT | FALLBACK
     │ (Only approved dial permits pass)
     ▼
  Call Allocator
     │
     ▼
  Telecom Provider (Provider A / Provider B)

CRITICAL INVARIANT:
The Pacing Engine has NO direct access to telecom providers. It can only propose.
The Safety Controller cannot be disabled, bypassed, or overridden.

--------------------------------------------------------------------------------
3.2. HOW SAFETY CONTROLLER WORKS FOR PROGRESSIVE DIALING (1:1 MODE)
--------------------------------------------------------------------------------
In Progressive Dialing:
• Rule: Exactly 1 outbound call per 1 available agent.
• The Safety Controller enforces:
    Approved_Dials = min(Requested_Dials, Available_Agents - Current_Ringing_Calls)
• If 5 agents are available and 2 calls are already ringing, max approved dials = 3.
• Guarantees 0 abandoned calls deterministically.

--------------------------------------------------------------------------------
3.3. HOW SAFETY CONTROLLER WORKS FOR PREDICTIVE DIALING (STATISTICAL MODE)
--------------------------------------------------------------------------------
In Predictive Dialing:
• The Predictive Engine proposes aggressive dials:
    D_raw = (A_available + A_expected_free) / p_answer - C_ringing
• The Safety Controller evaluates this proposal against 5 independent safety gates:

  GATE 1: ZERO-ABANDONMENT HEADROOM CHECK
    Limits total concurrent in-flight calls strictly to the available agent capacity:
      Approved_Dials = max(0, Available_Agents - Current_In_Flight_Calls)
    If requested dials exceed safe headroom, dials are reduced or rejected.

  GATE 2: AGENT AVAILABILITY SHOCK DETECTION
    Maintains a 5-second sliding window of agent availability.
    If available agent count drops by >25% (e.g. 40 agents log out simultaneously):
      Safety Controller immediately:
      1. Cancels all proposed dials (approved = 0)
      2. Enforces FORCE_PROGRESSIVE_FALLBACK
      3. Switches dialer to 100% deterministic 1:1 mode

  GATE 3: CIRCUIT BREAKER & PROVIDER HEALTH
    Monitors provider error rate and P95 latency.
    - If Circuit is OPEN: REJECT all dials (approved = 0).
    - If Circuit is HALF_OPEN: REDUCE dials by 75% for canary probing.

  GATE 4: MINIMUM AGENT THRESHOLD
    Predictive statistical models require a minimum law-of-large-numbers sample.
    If available agents < 3:
      Forces immediate PROGRESSIVE_FALLBACK (1:1 dialing only).

  GATE 5: HARD IN-FLIGHT CAPACITY LIMIT
    Caps total ringing calls so telecom network congestion cannot exceed buffer.

--------------------------------------------------------------------------------
3.4. SUMMARY OF SAFETY DECISION MATRIX
--------------------------------------------------------------------------------
| Condition                                | Decision                   | Action Taken                       |
|------------------------------------------|----------------------------|------------------------------------|
| Safe headroom & healthy provider         | APPROVE                    | Permit 100% of proposed dials      |
| Proposed dials risk agent overflow       | REDUCE                     | Cut dials to mathematically safe cap|
| 0 agents available                       | REJECT                     | Permit 0 dials                     |
| Provider Circuit Breaker OPEN            | REJECT                     | Block all dials                    |
| Circuit Breaker HALF_OPEN                | REDUCE                     | Reduce dials by 75%                |
| >25% agents drop within 5s (Shock)       | FORCE_PROGRESSIVE_FALLBACK | Immediate 1:1 progressive lock     |
| <3 agents available for predictive       | FORCE_PROGRESSIVE_FALLBACK | Fall back to safe 1:1 mode         |

4. COMPLETE END-TO-END SYSTEM WORKFLOW
================================================================================

Step 1: Pacing Engine Generates Proposal
  - Progressive Engine queries idle agents and proposes 1:1.
  - Predictive Engine applies Little's Law + Exponential Survival Function on
    connected agents + EMA answer rate to forecast capacity.
  - Generates `DialProposal { requestedDials, reason, mathTrace }`.

Step 2: Safety Controller Interception & Validation
  - Intercepts proposal before any network call.
  - Evaluates Headroom, Agent Shock, Circuit Breaker, and In-Flight limits.
  - Returns `SafetyVerdict { decision, approvedDials, riskScore, reason }`.

Step 3: Call Allocator & Atomic Concurrency Execution
  - Atomically reserves an available agent via Compare-And-Swap (OCC versioning).
  - Initiates approved dials via Telecom Provider interface.
  - No double-allocation possible (OCC guarantees single winner per agent version).

Step 4: Telecom Provider Processing & Webhook Delivery
  - Provider A (Reliable) delivers fast in-order events.
  - Provider B (Chaos) simulates jitter, duplicate events, and out-of-order webhooks.
  - Call State Machine enforces Idempotency (EventId dedup) and Skip-Ahead terminal guards.

Step 5: Borrower Answers Call
  - Agent transitions DIALING -> CONNECTED.
  - Call transitions ANSWERED -> CONNECTED.
  - Zero abandoned calls!

Step 6: Call Completion & Wrap-Up
  - Call completes -> Duration recorded in StatsCollector.
  - Answered call: Agent enters WRAP_UP (e.g. 1s for CRM notes) -> auto-returns to AVAILABLE.
  - Unanswered call: Agent immediately released to AVAILABLE (0 wrap-up idle waste).

Step 7: Watchdog Background Sweep (Crash Recovery)
  - Runs every 5-10 seconds.
  - If a worker crashes mid-reservation: Watchdog detects expired TTL lease and force-releases agent.
  - If a call is orphaned in INITIATED state: Watchdog recovers and marks FAILED.
  - If an agent is DIALING but call is COMPLETED: Watchdog frees agent.
